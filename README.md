# PORTX Game Launcher

An Android game library and launcher for extracted game folders, built with
Capacitor 6 (HTML/CSS/JS) + a custom native Java plugin.

## What's in this delivery

```
portx/
├── package.json, capacitor.config.json      — Capacitor project files
├── www/                                      — the whole UI (web layer)
│   ├── index.html
│   ├── css/style.css
│   └── js/{app,native,storage}.js
├── android-native/                           — native pieces to merge in
│   ├── java/com/portx/launcher/
│   │   ├── GameLauncherPlugin.java           — SAF, package install/launch, images, cache
│   │   └── MainActivity.java                 — registers the plugin
│   ├── manifest/AndroidManifest-additions.xml
│   └── gradle/build-gradle-additions.txt
└── BUILD_INSTRUCTIONS_TERMUX.md              — step-by-step build guide
```

`android-native/` is *not* a full Gradle project — Capacitor's own CLI
(`npx cap add android`) generates that scaffolding (the Gradle wrapper, the
full manifest, etc.) on your machine, and `BUILD_INSTRUCTIONS_TERMUX.md`
walks through merging these files into it and producing a debug APK.

## How importing and launching actually works

Android does not let an app silently execute an arbitrary file it finds in a
folder — only installed apps can be launched, and only the system installer
can install a new one. So "add a game folder" classifies what's inside it
into one of three real, working cases:

1. **The folder contains an `.apk`.** The launcher offers to install it
   through the system package installer (`installApk`). A game card doesn't
   have to stay apk-only, though: once you know the installed app's package
   name (shown by Android after install, or found with `adb shell pm list
   packages`), open the game's **details** panel and link it there — after
   that, Play launches it directly by package name instead of re-opening the
   installer every time.
2. **The folder contains a `package.txt` file**, or **you type a package
   name yourself** when adding the game (or later, from its details panel).
   Either way, the launcher checks `PackageManager` and launches the app
   directly by package name with `getLaunchIntentForPackage`. Manual linking
   is the main path for most real imports, since a generic extracted folder
   has no built-in way to say "this is already-installed app X."
3. **Anything else** (a native `.exe`/`.so`/ELF binary, or nothing
   recognizable, with no package linked) is reported honestly as unsupported.
   **This launcher does
   not, and cannot, make a PC game binary run on Android** — that needs a
   compatible runtime or engine (e.g. a Wine/Proton-style compatibility
   layer, or the game's own Android-native build), which is outside what a
   folder-import launcher can provide. The UI says this plainly instead of
   pretending the import worked.

This matches the brief's own requirement: *don't pretend selecting any PC
game folder automatically makes the game playable.*

## Game details panel

Tapping a card's gear icon opens a details drawer (not just a bare settings
list): a renameable title, the linked package name (editable, with a
"Save & check status" button that re-queries `PackageManager` on the spot),
an "open installer" shortcut when the imported folder had an `.apk`, and
read-only info — detected import type, size, date added, last played, and
the folder's source URI — plus Remove.

## App icon

A real adaptive icon ships under `android-native/res/`: a transparent
foreground glyph (the same "P" mark used in the in-app header) over a solid
navy background, legacy + round PNGs at all five mipmap densities for
pre-Android-8 devices, and a 512×512 copy for a store listing. Generated by
`android-native/icon-gen/make_icons.py` (Pillow) — rerun that script and
re-copy the output if you want a different mark or palette.

## Persistence

- Game library + per-game metadata + launcher settings: `@capacitor/preferences`
  (SharedPreferences-backed), via `www/js/storage.js`.
- Folder access: Storage Access Framework persistable URI permissions, taken
  in `GameLauncherPlugin.pickFolder()`, so the app can still read a folder
  after a restart without asking again (until the user revokes it from
  Android's own settings, which the OS can always do).

## Settings behavior

The settings drawer (resolution, FPS target, V-Sync, graphics preset, texture
quality) is stored per the brief, but is intentionally **not** wired to fake
"applying" these to games that can't honor them — most imported titles here
are regular installed Android apps with their own in-game options, which the
launcher can't override from outside. The per-game settings panel says this
explicitly rather than showing controls that do nothing. If you later target
a specific engine/runtime that does expose these knobs (e.g. a libretro core
or a specific SDK), that's where `GameLauncherPlugin` would grow a method to
pass them through.

## Known gaps / next steps

- Browser preview (opening `www/index.html` directly) shows the full UI but
  every native action resolves with a clear "needs the Android app" message
  — it's there for fast UI iteration, not for testing real launches.
- No code signing / release build config is included; `assembleDebug` only.
  For a Play Store or distributed release you'd add a signing config and use
  `assembleRelease`.
- `package.txt` is a convention invented for this project, not an Android
  standard — document it for your users, or replace that detection with
  whatever convention fits how you're distributing games.
